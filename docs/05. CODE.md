# Working on code

This chapter shows how to open a project, read its code, change code, and review a change in compos. Every step is an editor command, so the same keys work on a file, an agent's edit, and a diff.

## Start here

- Open a project with `⌘p` (find a file) or `⌘E` (open the project directory). A file opens in a mode chosen from its name.
- `⌥g i` lists the definitions in the buffer. `⌥.` goes to the definition of the name at point.
- `⌥x code-browse` reads a file as a tree. `h` and `l` go to the parent and the first child, `j` and `k` move between siblings, `Tab` folds, `Enter` leaves.
- `⌥x compile` runs the build without blocking the editor. `Enter` on an error line visits it, and `⌥x next-error` steps through the errors from any buffer.
- `⌃x v l` shows every accepted revision of the buffer, with the actor that wrote it.

## Open a project and a file

The project is the Git root. Commands that say "the project" use that root. `code-mode` puts a change and its buffers in one group named after the project, so the work stays together.

| Key | What it does |
| --- | --- |
| `⌘p` | Find a file in the project; ignored files stay out of the list |
| `⌘F` | Search the project with ripgrep, with a preview of each match |
| `⌘E` | Open dired at the project root |
| `⌃x ⌃d` | Open any directory in dired |
| `⌃x p p` | Enter a known project's group, then find a file in it |
| `⌃x p s` | Switch between this buffer and the project scratch buffer |
| `⌃x p k` | Kill every buffer of the project, and ask about unsaved files |
| `⌃x ⌃f` | Open a file by name, local or remote |

`Enter` in dired opens the file beside the listing and keeps the listing, so you can open another row. A file buffer follows its file: a change from Git or from a formatter merges into the buffer, and your unsaved work stays. Only a line that both sides changed stops a save.

Reference: [BUFFER](<FURTHER READING/BUFFER.md>), [groups](<FURTHER READING/groups.md>).

## A mode for every language

`prog-mode` is the base of every language mode. A key or a setting for every source buffer goes in `prog-mode-map` or `prog-mode-hook`. The editor picks the mode from the file name:

| Name | Mode |
| --- | --- |
| `.scm`, `.el` | scheme-mode |
| `.ex`, `.exs` | elixir-mode |
| `.heex` | heex-mode |
| `.rs` | rust-mode |
| `.json` | json-mode |
| `.html`, `.htm` | html-mode |
| `.py` | python-mode |
| `.go` | go-mode |
| `.c`, `.h` | c-mode |
| `.sh`, `.bash` | sh-mode |
| `.rb` | ruby-mode |
| `.js`, `.mjs`, `.jsx` | js-mode |
| `.css` | css-mode |
| `.md`, `.markdown` | morg-mode |
| `.org` | org-mode |
| `.txt` | text-mode |

`⌃⌥f` and `⌃⌥b` move forward and backward over one balanced form in most language modes. `(auto-mode-for-buffer BUF)` answers the mode a buffer would open in.

Tree-sitter gives a mode its colours, its outline, its folding, and its motion. A grammar is a separate install:

- `⌥x ts-grammars` lists the languages the editor can load.
- `⌥x ts-install-grammar` clones, compiles, and loads one grammar. It asks for a name such as `elixir`, `python`, or `scheme`.

A mode works before its grammar is installed. It edits, indents, and moves; only the faces and the tree-based outline wait for the grammar.

Reference: [MODES](<FURTHER READING/MODES.md>), [COMPLETION](<FURTHER READING/COMPLETION.md>).

## Read code by its structure

`imenu` is the index of the current buffer. Run it with `⌘i` or `⌥g i`. Type to narrow the list, and press `Enter` to go to a definition. When the buffer has more than one kind of definition, each kind gets a tab.

`code-browse` walks the parse tree. It is a minor mode, so the buffer keeps its major mode and its file.

| Key | What it does |
| --- | --- |
| `⌥x code-browse` | Turn structural browsing on or off in this buffer |
| `h` | Go to the parent node |
| `l` | Go into the first child |
| `j`, `k` | Next and previous node at this level |
| `Tab` | Fold or unfold the node at point |
| `Enter`, `q` | Leave code-browse |
| `⌥.` | Go to the definition of the name at point |

A file with more lines than `code-browse-fold-lines` folds its definitions when it opens. On a buffer with its own keys, such as a diff or a chat, `code-browse` refuses and says why.

`⌥.` is `goto-thing-at-point`. On a link it follows the link. On a source name it runs `code-goto-definition`: a buffer with a language server asks the server, and a buffer without one reads the file for the line that defines the name. In Scheme, `⌥.` is `scheme-goto-definition`, which searches the live sources.

In prose, including a chat, use the two verbs:

- `⌥x definition-show` shows the definition in the other window and keeps your focus. Run it again on the same name to go there.
- `⌥x definition-go` goes to the definition the other window shows.

Reference: [CODEBROWSER](<FURTHER READING/CODEBROWSER.md>), [CODE-BROWSER-PLAN](<FURTHER READING/internal/CODE-BROWSER-PLAN.md>).

## The Scheme IDE and its REPL

The editor is written in Scheme, and that Scheme is live. In a Scheme buffer:

| Key | What it does |
| --- | --- |
| `⌥.` | Go to the definition of the name at point, in the loaded sources |
| `⌃c ⌃d` | Echo the doc of the name at point |
| `⌃c ⌃z` | Go to the Scheme REPL you used last |
| `⌃c ⌃e` | Run the definition at point in that REPL |
| `⌥?` | Describe the name, the buffer, the mode, and its keys |

`⌥x apropos` searches the whole editor by words or intent: commands, keys, functions, modes, and settings. `⌥x command-palette` finds a command by what it does. Both are faster than a guess.

`⌥x repl` opens a new Scheme REPL. `⌥x scheme-repl` goes to the last one, or starts one.

| Key | What it does |
| --- | --- |
| `Enter` | Run the form at the prompt; an unfinished form gets a newline and an indent |
| `⌃j` | Break the line and indent, without running |
| `⌥p`, `⌥n` | Walk the history, over every form |
| `⌥↑`, `⌥↓` | Walk the forms that open with your typed text |
| `⌃c ⌥r` | Search the whole history for a form |
| `⌃c ⌃u` | Clear the prompt |
| `⌃c ⌥o` | Clear the transcript |
| `⌃c ⌃p`, `⌃c ⌃n` | Go up and down the transcript, entry by entry |
| `⌃c ⌃z` | Go back to the buffer you came from |

`*1`, `*2`, and `*3` hold the last three values, and `*e` holds the last error. The prompt keeps the history, so a restart does not lose it.

Reference: [SCHEME-THREADING](<FURTHER READING/SCHEME-THREADING.md>), [SCHEME-GOTCHAS](<FURTHER READING/SCHEME-GOTCHAS.md>).

## Language servers

`⌥x lsp-mode` turns the language server on or off for the current buffer. When `lsp-auto-start` is on, a file whose mode has a server starts it at visit. The stock registry has a server for Elixir (`elixir-ls`), JavaScript (`typescript-language-server`), Ruby (`ruby-lsp`), and Scheme (`scheme-langserver`).

| Command | What it does |
| --- | --- |
| `⌥x lsp-hover` | Echo the type or the documentation at point |
| `⌥.` | Go to the definition; a buffer with a server asks the server |
| `⌥x lsp-references` | List the references to the symbol at point |
| `⌥x lsp-diagnostics-list` | Show every diagnostic as a list |
| `⌥x lsp-next-diagnostic`, `⌥x lsp-prev-diagnostic` | Move between diagnostics |
| `⌥x lsp-show-diagnostic` | Echo the diagnostic at point |
| `⌥x lsp-status` | Echo every server connection |

The server's diagnostics show with a face as you edit. `⌥x lsp-references` opens a list; `Enter` visits a row.

Reference: [ARCHITECTURE](<FURTHER READING/ARCHITECTURE.md>).

## Structural editing with paredit

`⌥x paredit-mode` keeps the parentheses balanced while you edit. It is on by default in Scheme buffers, through `paredit-in-scheme-mode`.

| Key | What it does |
| --- | --- |
| `(`, `)`, `[`, `]`, `"` | Insert a balanced pair or quote |
| `Backspace`, `⌃d` | Delete backward or forward, and keep the text balanced |
| `⌃k` | Kill to the end of the line, balanced |
| `⌃⌥f`, `⌃⌥b` | Forward and backward over one expression |
| `⌃⌥u`, `⌃⌥d` | Out to the enclosing list, in to the next list |
| `⌃⌥k` | Kill the expression after point |
| `⌃⌥Space` | Set the mark after this expression |
| `⌃)`, `⌃(` | Slurp forward, or slurp backward |
| `⌃}`, `⌃{` | Barf forward, or barf backward |
| `⌥s` | Splice: remove the enclosing pair |
| `⌥r` | Raise: replace the enclosing list with this expression |
| `⌥(` | Wrap the next expression in a pair |

Slurp pulls the next expression into the list. Barf pushes the last expression out. Splice removes one level of delimiters.

Reference: [MODES](<FURTHER READING/MODES.md>), [SCHEME-THREADING](<FURTHER READING/SCHEME-THREADING.md>).

## Build, errors, and shells

`⌥x compile` runs a build and never blocks the editor. When `compile-command` is empty, it guesses from the project: `mix compile`, `cargo build`, `make -k`, `npm run build`, or `go build ./...`. Set `compile-command` to offer another command first.

The output streams into `*compilation:PROJECT*`, and the editor stays responsive while it runs.

| Key in the build output | What it does |
| --- | --- |
| `Enter` | Visit the file and line a row names |
| `n`, `p` | Next and previous error |
| `g` | Run the build again |
| `⌃c ⌃k` | Stop the build |
| `q` | Quit the output window |

From any buffer, `⌥x next-error` and `⌥x previous-error` step through the places the last build named. `⌥x recompile` runs the last command again, in its directory.

For a shell, `⌥x shell` opens the group's raw PTY, and `⌥x comint-shell` opens a text buffer that sends each line after the prompt. `⌃u` starts a new one. A shell survives a save and a reload. `⌥x tail-file` follows a file as it grows, local or remote.

Reference: [BEAM-POWER](<FURTHER READING/BEAM-POWER.md>), [TESTING](<FURTHER READING/TESTING.md>).

## The diff

`⌥x git-diff` shows the working-tree diff for the directory you are in. In a buffer of a project, `⌥x diff-mode` toggles the same diff for that file or that directory.

The diff opens as read-only cards, one card for each file. The tabs separate Changes from History. `?` asks the model to explain the selected hunk or file, and marks a file as explained.

| Key | What it does |
| --- | --- |
| `n`, `p` | Next and previous visible hunk, or file when all hunks are folded |
| `N`, `P` | Next and previous file |
| `Tab` | Fold the hunk; `f` folds its file; `F` folds all files |
| `1`, `2` | Show changes, or show history |
| `Enter` | Open the file at that line |
| `s` | Stage the hunk at point, or its file from the header |
| `?` | Explain the selected hunk or file |
| `m` | Show only conflicted files, or show everything again |
| `w` | Follow the tree on disk |
| `g` | Re-read the diff |
| `⌃c ⌃v` | Toggle between the cards and the plain diff |
| `q` | Close the diff |

`Esc` clears a selection, so `?` then explains the whole diff. The diff follows the tree when it is set to watch, so a save from the editor or from an agent appears in it.

Reference: [PROVENANCE](<FURTHER READING/PROVENANCE.md>), [KEYS](<FURTHER READING/manual/KEYS.md>).

## Git and jj

The editor uses Git for the project root and the diff. It uses jj when the checkout is a jj repository.

- `⌥x git-diff` shows the working-tree diff.
- `⌥x diff-mode` toggles that diff for the current file or directory.
- `⌥x chat-changes` shows what this chat changed: each jj change, its state, and the full diff.
- `⌥x jj-push` moves the tracked bookmark to the tip, then pushes to Git.
- `⌥x jj-recheck` looks for the jj binary again.
- `⌥x buffer-summary-log` shows a buffer's summaries and its jj changes, interleaved by time.

When `jj-autosave` is on in a jj checkout, a save snapshots the file, and one author's run becomes one change, not one change for each save. An agent run carries an `Agent:` line in the description.

Reference: [COMMITS](<FURTHER READING/COMMITS.md>), [PROVENANCE-CRDT](<FURTHER READING/internal/PROVENANCE-CRDT.md>).

## Provenance: who wrote this

Every buffer records the accepted revisions of its content. The record names the actor, the source, the operation, and the text each operation inserted or deleted. This is not Git history and does not need a file.

| Key or command | What it does |
| --- | --- |
| `⌃x v l`, `⌥x buffer-log` | List every accepted revision of this buffer, oldest first |
| `Enter` in the list | Describe the revision: its actor, source, operation, and hash |
| `n`, `p` | Next and previous revision |
| `⌥x buffer-log-show` | Show the selected revision beside the log, and keep your focus |
| `⌥x buffer-log-describe` | Visit the selected revision in full |
| `g` | Redraw the list |

The header of the list gives the recording state and the policy that set it. A save closes a changeset and writes a checkpoint. Provenance records before and after text, so it can retain deleted text and prompts; the header makes the recording state clear.

Reference: [PROVENANCE](<FURTHER READING/PROVENANCE.md>), [PROVENANCE-CRDT](<FURTHER READING/internal/PROVENANCE-CRDT.md>).

## Worktrees and task workspaces

A project is the primary checkout. A workspace is one task worktree of that project, and one workspace serves one task. A workspace for `/x/proj` named `NAME` lives at `/x/proj-worktrees/NAME` on branch `agent/NAME`. The worktree name, the branch, and the agent slug are the same string.

The `worktree-mode` header shows one state word from Git: `UNCOMMITTED`, `NEEDS REBASE`, `UNMERGED`, or `READY TO TEARDOWN`, with the counts.

| Command | What it does |
| --- | --- |
| `⌥x code-mode` | Start the agent coding workspace from this source buffer |
| `⌥x workspace-init` | Create or enter a task workspace in this frame |
| `⌥x workspace-new` | Create a workspace by name |
| `⌥x workspace-manage` | List the project's workspaces |
| `⌥x workspace-diff` | Diff a workspace against the primary branch |
| `⌥x workspace-land` | Merge a workspace into the primary checkout |
| `⌥x workspace-rebase` | Hand a rebase to the workspace chat |
| `⌥x workspace-cancel` | Cancel and remove a clean workspace |
| `⌥x workspace-chat` | Jump to the chat that owns a workspace |

`code-mode` asks before it creates a worktree. A buffer that is already in a workspace opens that workspace directly. In the `*worktrees*` list:

| Key | What it does |
| --- | --- |
| `Enter` | Open the workspace in dired |
| `=` | Diff the workspace against the primary branch |
| `r` | Rebase onto the primary branch, through the workspace chat |
| `L` | Merge into the primary checkout |
| `c` | Create a workspace |
| `a` | Jump to the workspace chat |
| `d`, then `x` | Flag a clean workspace for cancel, then confirm |
| `g` | Refresh the list |
| `q` | Quit |

Cancel removes only a clean worktree. The branch stays as a recovery path. Land refuses on unsaved work, uncommitted work, a dirty primary checkout, or no branch.

Reference: [WORKTREES](<FURTHER READING/WORKTREES.md>), [groups](<FURTHER READING/groups.md>).

## Remote files

A path that starts with `/ssh:` opens a file on another machine over ssh:

```
/ssh:user@host:/path/to/file
```

Type the path in `⌃x ⌃f`. The file opens as an ordinary buffer: its mode follows its name, and its keys work. Dired, save, rename, delete, and `⌥x tail-file` take the same form.

Reference: [FILE-VIEW](<FURTHER READING/FILE-VIEW.md>), [SCHEME-GOTCHAS](<FURTHER READING/SCHEME-GOTCHAS.md>).

## Format and indent

- `Tab` adds two spaces, through `indent-for-tab`.
- A parsed mode indents the line as you type and keeps the structure.
- In a JSON buffer, `json-mode` indents valid JSON when it opens, if `json-auto-pretty-print` is on. `⌃c ⌃f` formats again, and `⌥x json-pretty-print-buffer` does the same by name.
- The stock editor has no formatter command for every language. Run the project's formatter in `⌥x shell` or in `⌥x compile`.

Reference: [EDITING-SURFACE-SPEC](<FURTHER READING/internal/EDITING-SURFACE-SPEC.md>).

## For the agent

- Read code by structure. Ask `(code-outline BUF)` before you read a file, then `(code-read BUF LINE)` for one definition. Use `(code-find BUF TEXT)` to locate a definition by name. Do not read a whole file when one definition answers the question.
- Change one definition with `(code-replace! BUF LINE NEW)`, or one expression with `(code-sexp-replace! BUF ANCHOR NEW)`. Do not replace a whole file. Work on buffers by name, and do not move the user's windows, point, or focus.
- `code-mode` is the agent coding surface. It uses a task worktree and the coding prompt. Do not create a worktree without the user's consent.
- Verify with the focused test file first, and run the full sweep once before the commit. State the command and the result.
- The live catalogue wins over these notes. Some FURTHER READING documents describe a plan that the editor does not have. Read the live API with apropos before you trust a design note.
