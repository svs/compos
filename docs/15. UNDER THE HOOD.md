# Under the hood

This chapter explains how compos is built, in plain words, for a curious user. It shows the parts you can see and the parts that make them work. You do not need this to use the editor. Read it when you want to know why compos behaves as it does, or when you want to change it.

## Start here

Tell a new user these five things first:

- compos runs as one daemon on your machine. The daemon holds every buffer, window, chat and setting.
- The browser is only a view. It draws what the daemon sends and reports what you type.
- Elixir supplies the mechanism. Scheme decides the policy. You change the editor in Scheme, while it runs.
- Every buffer is its own process. A slow buffer does not stop the editor.
- The daemon is also an MCP server. An agent can read and change the live editor with Scheme.

## The daemon

`compos` starts one daemon. It serves the editor at `http://localhost:4004`. It keeps its state in `~/.compos`.

The daemon does not draw pixels. Each browser tab is a client that attaches to the daemon. The daemon sends each tab only the visible part of each window. The tab sends keys, scroll and geometry back. A tab can close and open again without a loss: the daemon holds the text, the point and the layout.

The daemon also saves the desktop to `~/.compos/desktop.etf`. After a restart, the windows, the buffers and the points come back.

| Command | What it does |
| --- | --- |
| `Ctrl-x d` | List the daemons and switch this tab to one |
| `Option-x restart-daemon` | Save the desktop and start the daemon again |

## Elixir mechanism, Scheme policy

The whole design follows one rule. Elixir supplies the mechanism. Scheme decides the policy.

Elixir owns the parts that touch the machine: sockets, PTYs, parsers, schedulers, the text NIF and the raw buffer mechanics. Scheme owns the parts that decide behaviour: commands, keys, modes, hooks, themes, dired, chat, display rules and the kernel itself.

This is why an agent can change almost anything while the editor runs. A new command, key, mode or view is Scheme. It takes effect at once, with no build and no restart. You can write the same Scheme in `~/.compos/*.scm`.

| Command | What it does |
| --- | --- |
| `Option-:` (`eval-expression`) | Run one Scheme expression now |
| `Option-x scheme-repl` | Open a live Scheme prompt |
| `Option-x load-file` | Load a Scheme file into the running editor |

## Processes, lanes and threads

Every buffer is a BEAM process. So is every agent, terminal and connection. Each one fails alone, and one crash does not take the editor down.

Scheme code does not run in one global queue. It runs on lanes. A lane is an ordered queue for one owner: the user interface, a group, a buffer, a connection, an agent. A lane keeps the order. A slow Scheme call holds its own lane and no other. The BEAM can interrupt a process that runs too long, so a keystroke on the user interface lane still runs while a long agent task works.

Reads are separate from writes. A reader takes a published row, so it never waits in the buffer's mailbox behind a save or a parse. This is a tail-latency fix: it removes the queue that a person feels as a frozen editor.

| Rule | Why |
| --- | --- |
| A process per real thing | One crash takes one part |
| A lane per owner | Order without one global queue |
| Writes to the process, reads to a read model | A read never waits behind a write |
| Publish before announce | A reader never sees old data after a change |
| A task for slow work | The editor lane never blocks |

Reference: [BEAM-POWER](<FURTHER READING/BEAM-POWER.md>), [SCHEME-THREADING](<FURTHER READING/SCHEME-THREADING.md>).

## The buffer store

The buffer process is the only writer of its buffer. It holds the text, the point and mark, the local variables and the undo history. It publishes one row to a shared table, the buffer read model. Browsers and agents read that row. A render therefore never queues behind a reparse, a checkpoint or a save in the buffer it draws.

Every change carries provenance: `user`, `editor`, `process` or `agent:id`. Provenance is load-bearing. Read-only blocks only `user` edits. The reactor ignores agent edits, so an agent cannot feed its own loop.

Overlays, folds and text properties use a persistent interval tree. One edit moves every range in one step, in logarithmic time. A reader that holds the old tree still sees the old positions.

| Command | What it does |
| --- | --- |
| `Ctrl-x Ctrl-b` | List every buffer, by group |
| `Option-x describe-buffer-locals` | Show this buffer's local variables |
| `Ctrl-x v l` | Show the provenance log of this buffer |
| `Option-x buffer-log` | Show every accepted revision of this buffer |

## The screen and the browser

The browser is a pure view. It knows no editor logic. The daemon sends rows of text as runs. A run carries its byte offset, its text and its face. The client draws the runs, the region and the cursor, and sends keys, scroll, geometry and selection back.

The editing surface is a `contenteditable` element. The browser owns text entry: dead keys, input methods, dictation, the native caret and the native selection. The daemon owns the text. The client reports intent, such as insert or delete, and Scheme decides what that intent means. A chat that the server draws is handled by the daemon alone.

A render sends only the visible slice. Fontification does not block the first paint. An edit shows the old faces at once and the fresh faces when they arrive, so the text never flashes plain.

Reference: [WINDOWS](<FURTHER READING/WINDOWS.md>), [FACES](<FURTHER READING/FACES.md>).

## The MCP socket

The daemon is a server on a Unix socket, `~/.compos/sock`. Its JSON-RPC method `eval` runs Scheme. That one method is the whole API. A script, an agent or a tool can do in one round trip what a person does with many keys.

A second socket, `~/.compos/sock-mcp`, speaks the Model Context Protocol to an outside agent. The agent sees a normal MCP server named `compos`. A small shim process connects it to the socket. The editor sees two Scheme calls.

The tool list is one registry. The in-editor chat and an outside agent read the same list. A tool that you add with `define-tool!` appears in both. Every tool declares its effects, so a read can run beside another read, and a write waits for them. Every call passes the same permission gate.

| Command | What it does |
| --- | --- |
| `Ctrl-c a m` (`mcp-hub`) | List every MCP server: status, tools, presets |
| `Option-x mcp-status` | Show the MCP server connections |
| `Ctrl-c b` (`llm-configure`) | Set up connectors, presets and bundles |

## Messages, telemetry and performance

The editor writes its own messages and errors to `*Messages*`. Open it with `Ctrl-h e`. It is the first place to look when something fails.

Telemetry collects one stream from every layer. A `scheme` row is a lane job or a task. A `live` row is the event, the state read and the render. A `browser` row is the round trip of one push, the DOM patch and the paint. Each keystroke carries a trace id, so the rows of one action share it.

| Command | What it does |
| --- | --- |
| `Ctrl-h e` (`view-messages`) | Show the messages and errors |
| `Option-x telemetry` | Show the duration of every layer's work |
| `Option-x telemetry-keys` | Keep only the keystroke rows |
| `Option-x telemetry-trace` | Narrow to the keystroke under point |
| `Option-x telemetry-slow` | Keep the rows over the slow threshold |
| `Option-x client-memory` | Show each browser frame's memory and its growth |

Reference: [SCHEME-THREADING](<FURTHER READING/SCHEME-THREADING.md>), [EVENT BUS](<FURTHER READING/EVENT BUS.md>).

## Packages and load order

The kernel is `apps/compos_core/priv/editor.scm`. The small standard library files load after it. Then the stock `priv/init.scm` runs, and that file lists every bundled package in dependency order. A package that needs another at load time requires it at its top. A second require is free, and a cycle is an error.

After the stock boot, your own config runs, in this order:

1. `~/.compos/ai-config.scm`
2. `~/.compos/init.scm`
3. `~/.compos/custom.scm`

`(load NAME)` searches the load path: the private directory, its packages, the project's `scheme/packages`, the config home and its packages. A package that the stock boot leaves out can mark a command with `;;;###autoload`. The command then exists in `Option-x`, and its first run loads the file.

The daemon watches the source roots. When you save a `.scm` file, it reloads the top-level forms whose text changed. When you save an `.ex` file, it compiles the changed modules and swaps them in. A restart is needed only for four changes: a new dependency, a change to the supervision tree, a NIF rebuild, or a change that moves registrations between tables.

| Command | What it does |
| --- | --- |
| `Option-x reload-file` | Reload a Scheme file into the live session |
| `Option-x load-file` | Load a Scheme file |
| `Option-x run-package-tests` | Run the tests that live beside the packages |

## For the agent

- Work on buffers by name. Do not move the user's windows, point, focus or scroll.
- Use `eval-scheme` to act on the live editor. `eval` is the whole API.
- The live editor wins over any document. When a document disagrees with the running editor, write the true thing and log the stale document.
- The buffer store never needs a restart. A change to a `.scm` file reloads itself on save.
- Before a change, load the code-change skill. Read `docs/ARCHITECTURE.md` once.
