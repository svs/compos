# Todos and workflows

This file is for the agent. Use it to tell the user how the shared todo list works, and how compos reacts to events on its own with listeners, workflows, cron jobs, webhooks and notices.

## Start here

- The todo list is shared. You and every agent read and write the same tasks, one list for each project.
- `M-x todo` opens the list for your group. `RET` opens a task, and `s` starts it and opens its chat.
- A task carries a goal, notes, a status and a log. Read the status first: it says what is done and what is left.
- Say "do X" and an agent files the task and works it through the todo API, not through the list.
- Compos can act on its own. A listener wakes a chat on an event, and a workflow, cron job or webhook reacts without a person.

## One list for the person and the agent

Every project keeps its tasks in a `todos.md` file. `todo-directories` finds them, by default `~/.compos/**/todos.md`. The list is one app for the person and every agent, so all of them read and write the same tasks.

`M-x todo` opens the list for the group you are in. `C-x t` does the same, and `C-x C-t` opens the todo keys. The list opens on the group you are in; `/` picks another group or All.

## The task is the record

A task is one heading in its project's `todos.md`. The file holds the same fields that `todo-get` answers: id, title, state, project, group, assignee, goal, notes, status, log, deadline, scheduled, priority, urgent, tags, depends, parent and source.

A task has four parts that carry the work:

- **Goal**: one line that says what is true when the task is done.
- **Notes**: the brief. It says what to do, why, and the rules.
- **Status**: where the task stands now. Write it for the person first, as `Done:` and `Left:`, each a few short lines.
- **Log**: the history. Add a line with `(todo-log ID TEXT [WHO])`.

The states are `inbox`, `todo`, `doing`, `waiting`, `review`, `done` and `cancelled`. A new task starts in `inbox`, and a person or an agent triages it to `todo`. A task in `review` waits for a person to approve it. A `done` or `cancelled` task reopens only to `todo`.

`(todo-create TITLE PROPS)` files a task and answers its id. PROPS must hold `'group`: the task shows in that group's list, and assigning it starts the chat there. PROPS may also hold `'project`, `'state`, `'priority`, `'deadline`, `'tags`, `'parent`, `'depends`, `'goal`, `'notes` and `'source`. A task with a `'source` is never filed twice.

## Working a task

An agent works a task through the API, not through the list:

- `(todo-get ID)` answers one task as a plist.
- `(todo-list SPEC)` answers the tasks, most urgent first. SPEC filters by state, project, assignee, tag, text, deadline, parent and source.
- `(todo-next WHO)` answers the most urgent ready task for WHO, else an unassigned one.
- `(todo-claim ID WHO)` takes the task and starts it.
- `(todo-update ID PROPS)` changes a field and logs each change. It sets the goal, the notes and the status.
- `(todo-done ID RESULT)` closes the task. The result becomes the status.
- `(todo-review ID SUMMARY)` hands the task to a person for an OK. The summary becomes the status, and the work stops there.
- `(todo-wait ID REASON)` parks the task on someone else.
- `(todo-cancel ID REASON)` closes the task as cancelled.
- `(todo-triage ID)`, `(todo-approve ID)` and `(todo-reopen ID)` move a task back into work.

A task that waits on a person goes to `review`. Do not continue it until the person approves. A task that waits on a message uses `todo-wait`, then a listener wakes the chat when the reply arrives.

## The list and the task page

The list and the task page are one app, one instance per group. Moving in the list changes nothing beside it. `RET` opens the task as its own page in the detail window, and `q` closes it.

The list opens with status tabs: open, inbox, waiting, closed and all. Left and right, or `v`, step the tabs, and each tab shows its count. `>` cycles the order: status, urgency, deadline, created, active. `<` cycles the sections: none, group, project, status. `/` filters by group, project and status, or by words such as `p:project`, `s:state`, `@assignee`, `#tag` and `!priority`.

The common keys on the list:

- `t` accepts the task: triage it, approve it from review, or reopen it.
- `s` starts it in `doing` and opens its chat.
- `d` marks it done, `x` cancels it, `W` parks it, and `i` sends it back to the inbox.
- `M-o` goes to its chat, or hands it to a new chat in a group.
- `N` adds a note, and `a` opens the action menu for every move and field.
- `c` files a new task, and `+` files a sub-task.
- `e` opens the task's file, and `k` dismisses the task.
- `SPC` marks a task, or `*` marks every row the filter shows. An action then runs on every marked task after it asks.

The task page has three tabs: overview, children and log. The overview shows the goal, the notes, the status, the details and the actions. The children tab lists the sub-tasks, and the log tab shows the history. The page sets the deadline with `D`, the project with `P`, the priority with `!`, and the urgent mark with `T`.

## Assigning, handover and review

`M-o` (`todo-assign`) hands a task to a chat in the group that filed it, else in the group you are in. `C-u` asks for the group first. A task with a chat opens that chat. A task without one gets a new chat, and that chat gets the task as its brief.

`(todo-assign-chat! ID GROUP [WHO])` is the same step for a coordinator chat. It makes the chat the assignee and sends it the brief. A chat that an agent starts stays out of the chat lists until the person asks for it.

`(todo-handover! ID [WHO])` archives the chat that works the task and starts a new chat with the task as its brief. Use it when a chat fills its context. The chat the person is on is never archived.

`(todo-done ID)` finishes a task; `(todo-review ID)` stops at the person's OK. `todo-dismiss!` closes the task's page and the chats that work it, without a change of state.

A chat can become a task with `M-x chat-todo`, and `M-x chat-goto-todo` shows the task a chat works.

## The event bus

Everything that happens outside a keystroke goes to one event log: a message came in, mail arrived, an agent finished a turn, a workflow ran. The log is one SQLite file, `~/.compos/events.db`, and it keeps each event on disk before it answers.

An event is a seq, a topic, a kind, data and a time. A topic names its family and its subject, for example `whatsapp:9198...`, `mail:recruiting` or `chat:...`. A topic pattern with a trailing `*` matches a prefix, and any other pattern matches one topic.

- `(event-publish! TOPIC KIND [DATA])` appends an event and answers its seq.
- `(event-subscribe! NAME PATTERN FN)` calls `(FN EVENT)` for each new matching event. NAME keeps its position across reloads and restarts, so it takes what it missed.
- `(event-log [PATTERN] [LIMIT])` answers the newest events in the log.
- `(event-define-view! NAME PATTERN STEP [INIT])` keeps a read model that folds each matching event.

`M-x events` opens the log as a list, newest first. `t` keeps one topic family, `T` shows every topic again, and `RET` shows the whole event beside the list. The list follows the head while it is on screen.

A topic that starts with `job:` is private to the chat that publishes it. Two chats can both use `job:tests` and never wake each other.

## Listeners

A listener makes a chat's agent wake on an event, so the turn can end and the work wakes it later. `(agent-listen! SPEC [NOTE])` answers the listener's id, and the agent gets the event as a message.

SPEC is a plist: `topic` (a trailing `*` matches a prefix), `kind`, `match` (text the event's data must hold), `task`, and `at`. `at` is a real time, such as `"2026-11-11 17:30"`. Use `at` only for a real time or as a fallback for work that cannot notify you.

`(agent-listeners)` lists the listeners, and `(agent-unlisten! ID)` stops one. Never end a turn while it waits on slow work without a listener, either on the event that ends the work or on a time.

## Workflows

A workflow is a supervised consumer of the log. It runs a Scheme handler exactly once for each batch of matching events:

```scheme
(define-workflow! "demo-triage"
  'listen   '("demo:wa:*" "demo:mail:*")
  'group-by 'demo-person
  'quiet    300
  'handle   'demo-triage)
```

`define-workflow!` takes `listen` (topic patterns), `handle` (a quoted function), `group-by` (the key for a group of events), `quiet` (a gap in milliseconds that joins a burst), `max-wait`, `batch`, `timeout`, `max-attempts`, `backoff`, `max-backoff` and `from`. The handler runs as `(HANDLE KEY EVENTS)` once for each group.

The handler has two kinds of step, and they do not mix. Inference answers questions and returns values. Code acts on the values, and every effect goes through `emit!` or `once!`.

- `(yes? QUESTION ABOUT)` answers a typed yes or no.
- `(pick QUESTION OPTIONS ABOUT)` answers one key, or `#f` for none.
- `(extract INSTRUCTIONS ABOUT FIELDS)` answers a list of plists.
- `(ask-model PROMPT ABOUT)` answers free text.
- `(emit! TOPIC KIND DATA [CAUSE])` writes an event, with its cause and trace.
- `(once! KEY THUNK)` runs THUNK once per KEY, and answers that value after.

A workflow's events, once keys, run record and position commit in one transaction, so a failed or timed-out batch runs again and nothing is written twice. An effect outside the log is at least once. Write an action that must not repeat as an intent event, and carry it out in a second workflow keyed by `once!`.

A failed batch retries with a growing backoff. After `max-attempts` the batch is parked, and the workflow moves past it, so one bad batch does not hold up the rest.

Control a workflow with `workflow-status`, `workflow-pause!`, `workflow-resume!`, `workflow-step!`, `workflow-rewind!`, `workflow-stop!` and `workflow-names`. `M-x events-demo` opens a scene with a producer, three workflows and a local model, so the person can watch the log and its traces.

## Cron

A cron job publishes an event on `cron:NAME`, and the cron workflow runs it. `(cron-define! NAME SPEC ACTIONS...)` defines or replaces one job:

```scheme
(cron-define! "morning" "@every 1h" 'command "agenda")
(cron-define! "sweep" "0 9 * * 1-5" 'emit '("feed:intent" sweep ()) 'zone "Europe/Oslo")
```

SPEC is a five-field cron time, or `@every 5m`, `@every 2h` or `@every 1d`. The action is `'command NAME`, `'call FN`, `'shell (DIR CMD)`, `'emit (TOPIC KIND DATA)` or `'agent (CHAT PROMPT)`. `'zone` names the time zone. A job is saved to `~/.compos/cron.scm` unless `'save #f`.

Cron answers the next run in unix seconds. `cron-jobs`, `cron-next-run` and `cron-last` read the jobs, and `cron-remove!` and `cron-run-now!` control one. A job that sends a prompt to an agent needs `cron-agent-jobs` on.

`M-x cron-list` shows every job with its time, next run and last run. `r` runs the job now, `k` removes it, and `g` redraws.

## Webhooks

A webhook turns an HTTP request into an event. `(define-webhook! NAME [OPTS] [HANDLER])` defines an endpoint at `/hooks/NAME`:

```scheme
(define-webhook! "mailgrip" (list 'token "secret" 'data 'json))
(webhook-attach-workflow! "mailgrip" 'read-mailgrip)
```

OPTS holds `'path`, `'methods`, `'token`, `'peers`, `'data 'json` and `'public`. A token is checked against the `x-webhook-token` header or a Bearer token. Without HANDLER, each request becomes a `webhook:NAME` event, and `webhook-attach-workflow!` runs a workflow for it. A request through the Cloudflare tunnel gets 404 unless the endpoint is `'public`.

The server listens on `127.0.0.1:4791` by default, and it starts only when `webhooks-enabled` is on or the person runs `M-x webhooks-start`. `M-x webhooks` lists the endpoints. There the person edits an endpoint, attaches a workflow, shows the request history and its payload, copies the URL, and starts or stops the server.

## Notifications

A notice tells the person that something needs them. `(notify! SOURCE TITLE [BODY] [PROPS])` publishes an event on `notify:SOURCE` and shows it in the corner for `notifications-seconds`, six by default.

PROPS is a plist kept with the notice: `'topic`, `'buffer`, `'jid` (a WhatsApp chat), `'command` and `'sticky`. A notice with `'buffer` leaves the screen when the person goes to that buffer, and a click goes there. A sticky notice stays until the person acts on it.

A notice leaves the corner after its time, and it stays in the history. `M-x notifications` lists the notices, newest first. `RET` goes where a notice points, `d` marks it done, and `g` redraws.

## Decide

`decide` is the typed decision service. A caller asks a question with a fixed answer shape, and a small model answers it. It is the same service behind `yes?` and `pick` in a workflow, and behind the permission checks for shell commands.

- `(decide-noul INSTRUCTIONS [CRITERIA])` is a yes or no question.
- `(decide-choice INSTRUCTIONS CRITERIA)` is a pick-one question.
- `(decide-score INSTRUCTIONS CRITERIA)` is a rated question.
- `(decide STATE QUESTIONS ...)` takes the typed questions directly and answers `(answers ((KEY VALUE) ...) usage (INPUT OUTPUT BACKEND ELAPSED-MS))`.

`decide-backends` lists the backends to try in order: `jev`, `laya` and `haiku`. `decide-config!` sets the order, and `decide-default` maps a purpose to a backend or a model id. `decide-async` runs the same call off the lane and hands the answer to a callback.

A workflow sends its inference to `decide` under the `fast` purpose. `yes?` counts an answer as yes at `workflow-yes-threshold`, and `pick` answers only a key that names a real option. A call may name a local model with `'model '(host "ssh:marilyn" model "qwen3:0.6b")`, an Ollama host, or an OpenAI-shaped host whose name ends in `/v1`.

## For the agent

- Work a task through the API. Read it with `todo-get`, take it with `todo-claim`, record progress with `todo-log`, and keep the status current with `todo-update`. Close it with `todo-done`.
- The status is for the person first. Use `Done:` and `Left:`, give the numbers that matter, and name the main file or function.
- A task that needs the person's OK goes to `todo-review`, and the work stops there until the person approves.
- File a task with `'group`. File it as `inbox` for the person to triage, unless the person says to start it.
- Use a `job:` topic for your own work. Another chat's `job:` event never wakes you.
- Never end a turn while slow work runs without a listener on the event that ends it, or on a time.
