code-browse

Read a source file with structural keys · priv/packages/code.scm + the ts-node primitive · Linear CB7 · updated 2026-08-14

What it is

M-x code-browse turns the current buffer into a reader. The buffer becomes read-only, single keys move over the structure of the code instead of over characters, the node you stand on carries a tint, and a long file folds its definitions so you see the signatures first. RET gives the buffer back, exactly as it was.

It is a MINOR mode: the buffer keeps its major mode, its syntax colors and its file. elixir-mode stays elixir-mode.

The reason it exists. An agent writes code faster than a human reads it. Reading is now the bottleneck, so reading gets first-class verbs: move by definition, fold what you do not need, tint what encloses you.

The keys

keycommandwhat it does
hcode-browse-parent Move to the node that encloses this one.
lcode-browse-child Move into the first block inside this node.
jcode-browse-next Move to the next node at this level.
kcode-browse-prev Move to the previous node at this level.
TABcode-browse-toggle-fold Fold or unfold the body of the node at point.
RET · qcode-browse-exit Leave the mode. Point stays where it is.
M-.code-goto-definition Go to the definition of the symbol at point.

Every motion lands point at the start of the node. The modeline shows browse <kind> — the grammar's own name for what you stand on (call, do_block, block).

The node

One shape carries everything: (KIND START END), in BYTE offsets, because point is a byte offset and tree-sitter reports bytes. There is no character math anywhere in this mode.

Landmine — a byte range does not name a node. Nested nodes can cover the SAME bytes. In Elixir, def alpha(x) is an arguments node and a call node over identical bytes. Ask "what follows the node at 27..35" and the parser answers about the inner call, which has no next sibling, so sibling motion stops one step in. The KIND travels with the range for this reason: ts-node climbs from the smallest node while the parent covers the same bytes, and stops at the kind the caller named.

Two backends, one question

The mode asks six questions — at, parent, child, next, prev, top — and two backends answer them.

backendwhenhow
tree-sitterThe buffer has a ts-lang local and the grammar parses it. The ts-node NIF walks the real syntax tree.
indentationEvery other buffer: an outline, a text file, a .scm (no grammar is wired yet). Pure Scheme over the lines. A block is one line plus the deeper lines below it. A sibling has the same indent, a parent has less, a child has more.

The mode picks the backend ONCE, on entry, and stores it in 'code-backend. Asking per keypress would reparse the file to learn something that does not change while you read.

Where the two differ

  • Entry. With tree-sitter, the node under point is usually an identifier — a word, not a place to stand — so the mode climbs to the first ancestor that spans more than one line. With indentation, every line is already a node, so it stands where you are.
  • Descent. l with tree-sitter skips to the first child that spans more than one line: the block, not the keyword before it. With indentation it takes the first child line.

Both share the anchor rule: point at the start of " def a do" means the def, not the block that holds it. Browsing starts on the code of the line, never on the indentation before it.

Folds

A node folds its BODY: from the end of its first line to its end. The first line stays on screen, so a folded definition still shows its signature and a … marker.

Folds are tagged (CB3): this mode owns the tag 'code and never touches org's or the diff's. TAB calls fold-toggle! and mirrors the result into 'code-folds.

The fold policy needs no language table

On entry, a file over code-browse-fold-lines (default 80) folds its definitions. What counts as a definition is decided by shape, not by a list of keywords per language:

fold the top-level nodes
  unless ONE node covers more than 4/5 of the file
    then fold the nodes inside it instead (up to three levels deep)

An Elixir defmodule wraps the whole file, so the rule descends through it and folds the defs. A Rust file has its fns at the top already, so the rule folds them where they are.

The tint

After every motion the mode replaces one overlay under the tag 'code-scope, using the face code-scope — a low-alpha background in all four base palettes (tokyo-night inherits from aimax-dark). There is no point-move hook: the tint is recomputed by the browse commands and by nothing else.

A node that covers the whole buffer gets NO tint. A tint over every line says nothing about where the reader is.

What survives a restart

Everything the mode does rebuilds from buffer-locals, because the setup fn runs on enable AND on desktop restore.
localholds
'code-nodeThe node the reader stands on.
'code-foldsThe fold ranges this mode owns.
'code-backend"ts" or "indent".
'code-savedWhat the mode clobbered: the read-only flag, the modeline text, and the prior binding of every key it takes.

The saved keys matter. A minor mode that binds j must give j back, so teardown restores the prior command or calls the new local-unset-key* primitive when there was none.

The setup fn also runs for a buffer that is NOT on screen, because desktop restore walks every buffer. The node primitives read the CURRENT buffer, so in that case the mode rebuilds the tint and the folds from the locals alone, and asks the parser nothing.

Go to definition — the LSP seam

This mode is syntax-level by design. M-. calls (lsp-definition SYM) when a language server binds that name, and otherwise searches the same file for a line that names the symbol after a defining word (def, defp, fn, class, …). One boundp check, no LSP code. The degradation is the same shape as tree-sitter falling back to indentation.

The primitive

(ts-node KIND START END OP)
  ;; KIND ""      -> the smallest node covering START..END
  ;; KIND "call"  -> that node, when nested nodes share the range
  ;; OP 'at 'parent 'child 'next 'prev 'top
  ;; -> (KIND START END), or #f

Mechanism in Rust, policy in Scheme: the NIF reports the tree and says nothing about what a reader should stop on. 'top is the ancestor whose own parent is the root — the fold policy's entry point.

Limits, today

  • Grammars are elixir, json and rust, plus any grammar loaded at runtime. Everything else browses by indentation.
  • The entry climb reparses the file once per step, up to three or four steps on a big file. It is fast enough to keep, and a cached tree per buffer version is the fix if it stops being fast enough.
  • The kinds in the modeline are the grammar's names, not friendly ones. That is honest, and a name table would be one more thing to keep true.
  • There is no global binding. The mode is M-x code-browse until a key earns it.
