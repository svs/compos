The MCP server

How an external agent gets the editor's tools - apps/compos_rpc/lib/compos/rpc/mcp_server.ex + scheme/packages/tools.scm - updated 2026-10-27

What it is

The editor keeps ONE tool registry in Scheme (define-tool!, served by llm-tool-specs). The in-editor chat reads that registry directly. An external ACP agent (claude-code, codex) runs as a subprocess and speaks MCP. The daemon serves the registry as MCP on its own Unix socket, ~/.compos/sock-mcp. The agent sees a normal MCP server named compos. The editor sees two Scheme calls.

Same registry, two consumers. The tool list an external agent gets from tools/list is the list the companion chat sends to the model. A tool added with define-tool! appears in both, with no second registration.

The pipeline

ACP agent (claude-code / codex)
   |  stdio MCP: initialize, tools/list, tools/call, ping
   v
compos-mcp-shim                about 1 MB per agent; sends the slug first
   |  the same MCP frames on ~/.compos/sock-mcp
   v
Compos.Rpc.McpServer           one connection process per agent, in the daemon
   |-- (mcp-proxy-tools-json)                  tools/list
   |-- (mcp-proxy-call name args-b64 author)   tools/call
   |        | permission gate (*permission-policy*)
   |        v
   |     the Scheme handler runs
   '-- Agent.ask_user                          the ask tool

The mcp package registers priv/native/compos-mcp-shim as the compos entry in each agent's session/new. The shim is a small Rust program with no dependencies (native/compos_mcp_shim). Compiling Compos.Core.McpShim builds it with cargo, as Rustler builds a NIF, so compos needs nothing more installed.

The shim does no MCP work. It sends the agent's slug (COMPOS_AGENT, which the ACP backend sets) as the first line. Then it copies stdin to the socket and the socket to stdout. An empty first line names no agent.

Why not nc: it is not on every system, and the versions differ. Debian's netcat-openbsd does not close its write side on stdin EOF without -N, and busybox often has no -U.

Why a socket, and not a process per agent

Until 2026-10-27, each agent started compos-mcp-proxy.exs: a complete BEAM VM that forwarded MCP to ~/.compos/sock. Each VM took 63-80 MB and about one second of CPU to boot. A chat that started 15 subagents booted 15 VMs at the same time. The daemon is already a BEAM, so the MCP work now runs there. An agent costs one shim process, about 1 MB, and no boot.

The transport stays stdio on the agent's side, so the agent behaves as before. A Unix socket has no idle timeout, so a long write and an ask that waits for the user keep working.

One connection

A connection is one agent session. The server reads the slug line, then one JSON-RPC frame per line. A Unix socket is a stream, so both ends assemble a frame until the newline.

rulewhat happens
order Consecutive read-only calls run together, each in its own process and lane. Any other message is a barrier: it waits for earlier reads and blocks later reads until it is done. readOnlyHint in the tools/list reply decides which calls are reads.
time limit 60 s for a read and 600 s for a write. A call past its limit returns an error that the model can retry. ask has no limit.
author The slug goes into mcp-proxy-call as agent:SLUG, so the agent's edits land in buffer-authors.
end When the agent closes stdin, the shim closes its write side. The server answers the calls in flight, then closes, and the shim exits. The listener sets exit_on_close: false for this: without it, the half-close drops the replies.
output Non-ASCII goes out as \uXXXX, because a strict client (Codex) rejects other escapes. A result that is not UTF-8 text returns an error. A result with the content prefix returns MCP content blocks (an image, for example).

Why base64

The server calls the Scheme side through an eval, and an eval returns a printed Scheme value. Printed-string escaping is not JSON-safe for every byte. So the server encodes the MCP arguments as base64 before the eval, and the Scheme side encodes its result before the print. The server strips the quotes from the printed value and decodes.

The permission gate - the third chokepoint

Every deny-listed verb reaches the world through one of three gates: the api lane's tool loop, the ACP permission banner, and this server. mcp-proxy-call asks the SAME *permission-policy* the other two ask.

verdictwhat happens
allow / allow-always The call dispatches to the Scheme handler. An "always" answer is kept for the verb in the chat's group.
ask The call raises a card in the agent's chat, through the same door the ACP lane uses. The user answers it as any other card. With no chat to ask in, the call is refused.
deny Refused, with the deny-listed verb named (permission-denied-verb?).

The Session

A read-only call and an eval whose whole program is one shell command do not hold the Session. mcp-proxy-call takes a deferred reply (eval-defer!), runs the work in a Task, and answers with eval-resolve!. Keys and redraws run meanwhile. A write runs in the Session, in the agent's chat frame, with the edit author set.
