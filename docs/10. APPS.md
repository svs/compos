# Apps

This chapter tells what an app is in compos, how to use one, and how to ask for a new one. Mail, issues, chat and other outside services have their own chapter, [11. CONNECTED APPS](<11. CONNECTED APPS.md>).

## Start here

Tell a new user these first:

- An app is a list with one row per thing, a page for each row, and the same actions on both.
- One command opens an app, and it opens in its own group. The group saves and restores the whole app layout.
- Every app uses the same list mode. So the same keys mark, filter and act everywhere.
- Move the point down the list and the page beside it follows.
- To get a new app, ask the agent. It writes the app in Scheme while the editor runs.

## What an app is

An app is three things:

1. A listing: one selectable row for each thing.
2. A page for each row, in a buffer of its own beside the listing.
3. Actions: the same verbs on both, under the same keys.

compos often brings an outside service into the editor as an app. Then its data is in a buffer, and an agent can read it there without a chain of tool calls.

Reference: [INTRODUCTION](<FURTHER READING/INTRODUCTION.md>), [LISTS](<FURTHER READING/LISTS.md>).

## The list keys

An app's listing is a list mode. The same keys work in every app, and in ibuffer, dired and the chat list.

| Key | Does |
| --- | --- |
| `Space` | Mark the row at point; `m` does the same |
| `u`, `U`, `*` | Unmark one row, unmark all, or mark all |
| `x` | Run the marks: the mode's verb on every marked row |
| `/` | Narrow the rows on every key |
| `f` | Filter the rows on every key; `\` widens by one filter |
| `<`, `>` | Cycle the declared sections and the declared order |
| `Enter` | Open the row: its page, or a new buffer for it |
| `Tab` | Fold the rows under the row at point |
| `n`, `p` | Walk up and down the rows |
| `g` | Read the rows again |
| `?` | Show every key of this list |
| `q` | Quit the list |
| `Ctrl-.` | Act on the thing at point |

A row keeps the parsed record, not a printed line. So an action on a row has the whole record.

Reference: [LISTS](<FURTHER READING/LISTS.md>), [CHAT-LIST](<FURTHER READING/CHAT-LIST.md>).

## Pages

An app uses one page for each row, not one page that it rewrites. Each page keeps its own point, its own scroll and its own name, such as `*sentry:ISSUE*`.

| Key | Does |
| --- | --- |
| `` Ctrl-` `` | Walk the pages opened from this listing, the most recent first |
| `` Ctrl-Option-` `` | Walk them the other way |
| `Option-Enter` | Keep this page: it takes a name of its own, and the next row opens a fresh one |
| `q` | Quit the listing and take its pages with it |

The listing opens a page in one remembered window. Later rows retake that window, so the frame never grows a pane for each row. On a wide frame the three parts stand as columns: the group chat, the listing and the current page.

A page can be a rendered page instead of text. It is HTML in a sandbox: no JavaScript runs, and all behaviour is Scheme. A link in the page is an action, not a navigation.

Reference: [COMPONENTS](<FURTHER READING/COMPONENTS.md>), [COMPOSML](<FURTHER READING/COMPOSML.md>).

## Actions

One verb, one key, both places. The listing reads the row at point; the page keeps its record in a buffer-local. Both keys call the same function.

An action reports itself: a message on the way in, a message with the result, and the raw failure in the app's own log buffer. An action that fails silently is a bug report that never arrives.

An action that leaves the editor, such as a send, a cart or a purchase, is the user's click. The agent wires it and does not fire it.

Reference: [COMPONENTS](<FURTHER READING/COMPONENTS.md>), [groups](<FURTHER READING/groups.md>).

## The app registry

`Option-x app-registry` lists every app in the editor, in three sections:

- `user`: your own packages under `~/.compos/packages`.
- `package`: apps you installed with `package-install`.
- `core`: apps that ship with compos.

Moving the point shows the app's page beside the list: its modes, its commands and its open buffers.

| Key | Does |
| --- | --- |
| `Enter`, `o` | Open the app |
| `v` | Visit the app's source in the other window |
| `/` | Narrow the rows |
| `g` | Read the apps again |
| `q` | Quit |

The registry reads the live editor, so it shows an app the moment the app loads.

## Getting a new app

Ask the agent. For example: make me a Sentry app. Put the API key in your secrets, and the agent writes the app in Scheme while the editor runs.

An app can have an action on a row, such as a button that asks an agent to fix an issue. It can also open a form, a preview page, or a new group of its own. The request is enough; the agent decides the shape.

Reference: [COMPONENTS](<FURTHER READING/COMPONENTS.md>), [COMPOSML](<FURTHER READING/COMPOSML.md>), [11. CONNECTED APPS](<11. CONNECTED APPS.md>).

## For the agent

- Load the `app-creator` skill before you build an app. It owns the four invariants.
- Give the app one home group, and make every render join it. The entry command enters the group.
- Make the listing a list mode with `'transient #f`. Rows are records; `'cells` renders them.
- Open one page per row with `display-buffer-detail!`. Never move a page with `switch-to-buffer!`, `pop-to-buffer` or a bare `display-buffer`.
- Hand the app's three panes to the responsive tiler. Do not split by hand and do not hardcode a width.
- Name the app once, and name its group, buffers, modes, commands and settings after it.
- Check the result in `Option-x app-registry`, and open the app to confirm one frame holds the listing and its page in the app group.
- Leave per-service detail to [11. CONNECTED APPS](<11. CONNECTED APPS.md>). This chapter owns the shape of an app, not one service.
