# Models and connectors

This file is for the agent. Use it to tell the user how compos reaches a model: how to connect a provider, how to choose a model for one chat, and how each job gets a model. Speak in plain words and give the keys.

## A connector runs a model

A **connector** is the program or server that reaches a model. A **model** is the id that the connector runs. compos has three kinds of connector:

| Kind | Examples | What it needs |
| --- | --- | --- |
| **agent** (ACP) | claude-code, codex-app-server, opencode, opencode-go, kimi, gemini, deepseek | the agent program, and its own sign-in |
| **API** | Anthropic, OpenAI, OpenRouter, DeepSeek | an API key |
| **browser** | gemini-nano | Chrome with the compos extension |

An agent connector runs a full agent program. The direct API connector calls the provider itself. The browser connector uses the model in Chrome.

Reference: [CHROME_EXTENSION](<FURTHER READING/CHROME_EXTENSION.md>), [PROMPTS](<FURTHER READING/PROMPTS.md>).

## Connect and test a connector

`M-x llm-connectors` opens the list. It shows every connector, its kind, what it still needs, how many models it offers, and its last test. `M-x setup` opens the same work as a guided wizard.

| Key | What it does |
| --- | --- |
| `i` | install the agent program |
| `l` | sign in (the agent's own login) |
| `k` | add or change the API key |
| `t` | send one short test message and time the reply |
| `T` | test every ready connector at once |
| `d` | make this connector, or the model on this line, the default for new chats |
| `a` | add a hosted provider, or a server of your own |
| `RET` | show the connector's page and its whole last test |
| `g` | check every connector again |

A test sends one short message and times the reply. The list keeps the last result for each connector and each model, also across a restart. A failure shows the error from the provider.

To add a provider of your own, use `a`. Give it a name, an address, and a shape (`openai` by default). compos asks for its key and tests it.

Reference: [1. SETUP](<1. SETUP.md>).

## Choose the model with C-c b

`C-c b` (`M-x llm-configure`) edits the whole setup of the current chat:

| Key | Field |
| --- | --- |
| `b` | the connector (backend) |
| `m` | the model |
| `e` | the reasoning effort |
| `p` | MCP servers and tool presets |
| `+` | more: prompt sections (`i`), sandbox (`x`), tool surface (`t`), show prompt (`v`), always asks (`d`) |

The menu edits one config and shows what it would change. `ESC` gives the config to the chat without saving it. To keep it, save it as a preset. A group's new chats take the group's preset; if the group names none, they take `llm-default-bundle`.

A model that lists effort offers it. A model that lists none shows no effort. The picker reads the connector's own model list when the connector is live, and the model catalog otherwise.

Reference: [AGENT CONTEXT MANAGEMENT](<FURTHER READING/AGENT CONTEXT MANAGEMENT.md>).

## A preset gives each job one model

Some jobs run all the time: summaries, titles, code browsing. Each job uses a named role, and `llm-model-presets` says which model each role uses.

| Role | Used for |
| --- | --- |
| `default` | new chats, and every job that names no role |
| `fast` | short jobs, and the `haiku` backend of the decision model |
| `summarize` | running summaries, code browser summaries, content scale |
| `coding` | code agents |
| `image` | image work |

An empty role uses the session model. This is expensive for the jobs that run all the time: a small model for `fast` and `summarize` is the point. Set them in `C-c b`, or as a setting:

```scheme
(customize-save! 'llm-model-presets
  '((default . "claude-sonnet-5-5") (fast . "claude-haiku-4-5-20251001")
    (summarize . "claude-haiku-4-5-20251001") (coding . "claude-opus-5-5")))
```

Check: `(llm-model-for 'fast)` names the model you set.

Reference: [1. SETUP](<1. SETUP.md>), [AGENT CONTEXT MANAGEMENT](<FURTHER READING/AGENT CONTEXT MANAGEMENT.md>).

## A bundle is a whole setup under a name

A **bundle** is a connector, a model, an effort, a list of tool presets, the prompt sections it turns off, and its permissions and sandbox, saved under a name and a key. A group says which bundle its new chats start with.

| Call or command | What it does |
| --- | --- |
| `M-s` in `C-c b` | save this setup as a new bundle |
| `M-u` in `C-c b` | update an existing bundle |
| `M-n` in `C-c b` | a new bundle from a connector, a model and an effort |
| `M-d`, `M-g` | make it the default, or the default for this group |
| `M-x group-llm` | choose the bundle a group's new chats start with |
| `(llm-default-bundle-apply! BUF)` | the same rule, for a chat an agent starts |

A change to a bundle affects new chats. An open chat keeps the presets it has.

Reference: [AGENT CONTEXT MANAGEMENT](<FURTHER READING/AGENT CONTEXT MANAGEMENT.md>).

## MCP servers and the MCP hub

An **MCP server** gives the agent tools. A **tool preset** bundles servers, a prompt that says how to use them, and the names that apropos ranks first.

`C-c a m` (`M-x mcp-hub`) lists every server. It shows the status, the tools and the presets of each server. From the list you can start, stop and restart a server, and read its frames. `M-x chat-tool-surface` shows the servers that the current chat holds.

A person adds a server in `~/.compos/ai-config.scm`:

```scheme
;; stdio: the editor starts this program
(mcp-register! 'name '(command "npx" args ("-y" "package")))
;; http: the editor connects to this address
(mcp-register! 'name '(url "https://host/mcp" headers (authorization "@MY_TOKEN")))
```

A `@VAR` in a url, an env value or a header is a key reference. The editor resolves it just before it connects, so the config file holds no secret. The editor refuses `mcp-register!` from an agent: a server is the user's choice. Turn its tools on for a chat with `p` in `C-c b`.

Reference: [AGENT CONTEXT MANAGEMENT](<FURTHER READING/AGENT CONTEXT MANAGEMENT.md>), [MCP server](<FURTHER READING/mcp-proxy.html>).

## Permissions and the sandbox

Every tool call passes a gate. The chat's stance decides when the gate stops to ask:

| Stance | Meaning |
| --- | --- |
| `ask` | every tool call asks |
| `approve` | only irreversible acts ask |
| `auto` | the agent stops asking too; the deny-list still holds |

The editor's own commands use their catalogued effects. `pure` and `read` run. `destroy` and `spend` ask. Shell commands go through the shell gate, which asks `decide` about each command. A question that the user answers with **Always** becomes a standing rule for that chat.

The agent's own file tools follow `agent-filesystem-tools`:

| Value | Meaning |
| --- | --- |
| `deny` | the agent edits buffers, and saves them (default) |
| `ask` | each direct write asks first |
| `allow` | the agent writes files itself |

The **sandbox** limits where an agent's shell commands may write. It is on by default: a command writes only in the chat's directory, the temp directories, and the tool caches. `agent-sandbox` sets it for every chat. A group sets it for its own chats. In `C-c b` the value is `on`, `off`, or `group`.

`M-x llm-config-permission-report` shows the whole policy for a chat: the stance, the agent mode, the file tools, the shell gate, and every standing rule.

Reference: [PROMPTS](<FURTHER READING/PROMPTS.md>).

## JEV and the fast model

The editor asks short, typed questions all the time: yes or no, pick one, give a score. The shell gate asks about each command. `decide` sends these questions to a decision backend, in the order of `decide-backends`:

- `jev`: TypeSafe System One. It is a user package, so a fresh install does not have it. It needs its own key.
- `laya`: a model on this machine. It needs Apple silicon, a python with `laya_mlx`, and a checkpoint.
- `haiku`: a hosted model. It needs an Anthropic key, and it uses the `fast` preset.

A fresh install does not need a decision model. `apropos` falls back to word matching, and that is enough for an agent to find the editor API. Do not let the user stall on it.

When JEV is not there, use the fast model of the agent the user already has. Put it in the `fast` and `summarize` roles, keep `jev` out of `decide-backends`, and set `command-palette-decide-backend` to `model`.

Check: `(llm-model-for 'fast)` names that model, and `decide-backends` does not name `jev`.

Reference: [1. SETUP](<1. SETUP.md>), [EVENT BUS](<FURTHER READING/EVENT BUS.md>).

## Secrets come from the key chain

compos never stores a key in a buffer or in a log. It reads a key from the environment first, then from the key files in `~/.compos`, then from Doppler. `M-x setup` stores each key with the secret tool that the person uses: Doppler, 1Password, GPG, the macOS Keychain, or the Linux Secret Service.

`(setup-secret-backends)` lists the tools on this machine, without any value. `(secret-set? 'NAME)` says whether a key is there. `M-x setup` is where the person types or signs in; an agent never reads, prints, or stores a key value.

Reference: [1. SETUP](<1. SETUP.md>).

## The model catalog and its rules

compos keeps a catalog of the models that providers offer: their ids, names, context, and reasoning controls. Elixir fetches and caches the catalog. What an entry means is editor policy: which effort and thinking controls to offer, which model list a live backend gives, and how old a snapshot is. `llm-catalog-max-age-days` sets the age limit, seven days by default.

`M-x llm-catalog-status` says what catalog is loaded and how old it is. `M-x llm-catalog-refresh` fetches the newest catalog now. `M-x llm-models-refresh` asks each provider for its own list.

A live connector's own list is authoritative for its session. The catalog fills the gaps, and the picker reads it per row without a call for each model.
