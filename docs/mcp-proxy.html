The MCP proxy

How an external agent gets the editor's tools · priv/compos-mcp-proxy.exs + priv/packages/tools.scm · updated 2026-08-14

What it is

The editor keeps ONE tool registry in Scheme (define-tool!, served by llm-tool-specs). The in-editor chat reads that registry directly. An external ACP agent (claude-code, codex) runs as a subprocess and cannot — it speaks MCP. The proxy is the bridge: a small stdio MCP server that forwards each MCP request to the daemon's JSON-RPC socket. The agent sees a normal MCP server named compos. The editor sees two evals.

Same registry, two consumers. The tool list an external agent gets from tools/list is byte-for-byte the list the companion chat sends to the model. A tool added with define-tool! appears in both, with no second registration.

The pipeline

ACP agent (claude-code / codex)
   │  stdio MCP: initialize · tools/list · tools/call
   ▼
compos-mcp-proxy.exs           one process per agent session; OTP :json, no deps
   │  JSON-RPC eval on ~/.compos/sock (COMPOS_SOCK overrides)
   ▼
daemon Session ── (mcp-proxy-tools-json)          tools/list
              └── (mcp-proxy-call name args-b64)  tools/call
                     │ permission gate (*permission-policy*)
                     ▼
                  llm-tool-call → the Scheme handler runs

The mcp package registers the proxy as the compos entry in each agent's session/new, so every agent session spawns its own proxy process. The proxy handles four methods: initialize, tools/list, tools/call, and ping. Everything else gets -32601.

Why base64

The RPC socket's eval returns printed Scheme values. Printed-string escaping is not JSON-safe for every byte, so a raw JSON payload can break in either direction. Both entry points therefore move payloads as base64: the proxy encodes the MCP arguments before the eval, and the Scheme side encodes its result before the print. The proxy strips the quotes from the printed value and decodes. Base64 survives both transports untouched.

The permission gate — the third chokepoint

Every deny-listed verb reaches the world through one of three gates: the api lane's tool loop, the ACP permission banner, and this proxy. mcp-proxy-call asks the SAME *permission-policy* the other two ask. It used to apply the deny-list alone — which meant a chat in ask mode was in ask mode everywhere except here.

verdictwhat happens
allow / allow-always The call dispatches to the Scheme handler.
ask Refused, fail-closed. A proxy call arrives on the socket from an agent the editor does not render — there is no chat to raise an Allow/Deny banner in, so nobody can answer one. The refusal text tells the agent to ask the user to run it, or to approve it in the chat.
deny Refused, with the deny-listed verb named (permission-denied-verb?).

The open edge (R5)

mcp-proxy-dispatch runs the handler in the session. The names it dispatches come from the Scheme registry, and a Scheme handler runs in the Session GenServer by definition — the same single-threaded interpreter every keystroke goes through. The "never dispatch in the session" rule in mcp.ex is about MCP tools on other servers; mcp-call! obeys it for those by running in a Task. This surface cannot: the handlers ARE Scheme.

Consequence: a slow handler stalls the editor while it runs, because the socket's request holds the session until the eval returns. The fix needs a deferred-reply RPC design — the socket request returns at once, the session queues the work, and the reply is delivered when the handler finishes. This is the last open piece of the AI-native refactor.
