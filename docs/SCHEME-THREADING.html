How Scheme multithreading works

ai-max.el interpreter and execution lanes - current implementation - updated 2026-08-23

Short version: many BEAM processes can evaluate against one Scheme world. Each lane stays serial. Different lanes run concurrently. Set AIMAX_SCHEME_EXECUTION=single_actor to route ordinary Scheme through one worker. Explicit isolated actors remain optional; see docs/SCHEME-ACTORS.md.

The mental model

The old Session process executed all Scheme code. A long RPC evaluation could delay a keystroke. The current Session stores only an interpreter handle. Lane workers execute the code.

A lane is a GenServer worker with a FIFO mailbox. The worker runs one job at a time. The supervisor creates workers only when required. An idle worker exits after five minutes.

An ordinary Scheme expression stays sequential. It can explicitly fan work out with task-spawn, task-run!, or chat-parallel-map. Each task is a supervised BEAM process over the same booted environment; no environment snapshot is copied. The LLM tool loop does this automatically when a round contains only pure/read tools, with a global admission cap across agents.

Scheme.exec is the required boundary for every evaluator entry point. An error drops private frames. Writes already made to shared frames remain.

What a lane protects

  • Job order for one owner.
  • Re-entry without self-call deadlock.
  • The UI from unrelated slow work.
  • The queue from one raised job.

What a lane does not protect

  • Globals shared by different lanes.
  • Multi-binding transactions.
  • Read-modify-write updates across lanes.
  • External effects before an error.

The two-tier environment store

The interpreter handle contains an ETS table identifier and the global frame reference. Every lane receives the same handle. Closures capture frame references, not snapshots.

During boot, all frames stay local for speed. After package loading, one sweep removes dead frames. The loader then publishes the survivors. Normal executions use the selective flush.

ETS writes become globally available immediately. Another running execution can hold a cached old value. The cache resets at the next Scheme.exec boundary.

A complete evaluation is not a transaction. Two lanes can interleave global reads and writes. Concurrent increments can lose an update. Use the same lane when an invariant spans multiple operations.

The short stale-frame window

A primitive can expose a closure before its evaluation finishes. The evaluator now publishes the closure's reachable frames before invoking that primitive, so another lane can call it immediately. Later mutation of the promoted frame writes through to the shared store.

Garbage collection and cancellation

The environment GC uses reachability. Roots include the global frame, commands, escaped callbacks, minibuffers, and buffer locals. The Session checks every 30 seconds. It sweeps after the frame count more than doubles.

In-flight rows use worker PIDs. GC removes rows for dead workers. The GC claim also stores its sweeper PID. New evaluations remove an orphaned claim.

Lane.kill terminates only the worker. The shared store and buffers survive. Queued jobs do not survive. The next call creates a new worker.

Worked race example

;; Lane A and lane B share this binding.
(define counter 0)

;; Both lanes can read 0 before either writes.
(set! counter (+ counter 1))

;; The final value can be 1, not 2.

Questions for design review

  1. Is one group the correct serialization boundary? One slow agent callback holds all Scheme work for that group.
  2. Which globals require atomic operations? Counters, registries, and read-modify-write state can race.
  3. Should Scheme expose lane selection? Elixir call sites select lanes today.
  4. Which synchronous waits must become actors? In single-worker mode, a wait cannot block the worker that must deliver its callback.
  5. Should GC remain stop-the-world? A larger store can make the pause visible.
  6. Which callbacks still use :ui? Async producers need explicit lanes to protect input.
